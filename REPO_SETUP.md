## 2. Yes — you can store this on GitHub and run it locally

That's exactly what git is for. Three things to get right first.

### ⚠️ (a) Don't put the git clone inside OneDrive

Your folder today is `C:\Users\megha\OneDrive\Documents\Reading`. OneDrive syncs the hidden
`.git` folder file-by-file in the background, which reliably corrupts repositories —
phantom `.lock` files, "index is corrupt" errors, and `.git` objects turning into
"conflicted copy" duplicates. OneDrive and git both want to be the thing syncing that
folder, and they fight.

**Split them:**

```
C:\Users\megha\book-tools\                     <- git clone (code)   — synced by GitHub
C:\Users\megha\OneDrive\Documents\Reading\     <- data               — synced by OneDrive
C:\Users\megha\OneDrive\Pictures\...\Books\    <- screenshots        — synced by OneDrive
```

This works with almost no code changes, because the scripts already point at the data with
absolute paths (`EXCEL_PATH = Path(r"C:\Users\megha\OneDrive\Documents\Reading\books_output.xlsx")`).
The `.py` files find each other via `SCRIPT_DIR`, so they can all move together. Each half
keeps syncing through the tool that's actually good at it, and you get real version history
and rollback on the code.

### ✅ (b) Path mismatches — fixed

Every script now uses the same two constants:

| Constant | Points at | Holds |
|---|---|---|
| `SCRIPT_DIR` | wherever the `.py` files live | code, `launcher_config.json` |
| `DATA_DIR` | `...\OneDrive\Documents\Reading` | spreadsheets, `logs/` |

Four places disagreed about this, all invisible today because code and data share a folder,
and all of which would have broken the moment you cloned to `book-tools`:

1. `storygraph_to_read.py`, `amazon_owned_books.py`, `storygraph_diagnostic.py` read
   `launcher_config.json` from the **data** folder, but `book_launcher.py` writes it to the
   **code** folder — your saved Settings would silently stop applying.
2. `reenrich_existing.py` looked for `books_output.xlsx` **next to itself**, so
   "Fill Missing Metadata" would fail to find your spreadsheet.
3. `amazon_owned_books.py` loaded `books.py` from a hardcoded OneDrive path rather than
   from its own folder, so it would import a stale copy of the code.
4. The launcher's "View Latest Log" read `SCRIPT_DIR/logs`, but the scripts *write* logs to
   `DATA_DIR/logs` — the button would report "no logs found".

Each lookup tries the correct folder first and falls back to the old one, so this works
**before and after** you move the code. Nothing breaks in the meantime.

### 🐛 (b2) A syntax error that was blocking StoryGraph entirely

`storygraph_to_read.py` had a broken line — a statement welded onto the `elif` above it:

```python
elif click_to_read(page):            result[STATUS_COL]    = "Added"
    result[NOTES_COL]     = "Clicked To Read"
```

That's an `IndentationError`, meaning **the whole file failed to parse and "Push to
StoryGraph" could not run at all** — it would have died before opening the browser. Looks
like an editing accident at some point after the April run log was written. Now:

```python
elif click_to_read(page):
    result[STATUS_COL]    = "Added"
    result[NOTES_COL]     = "Clicked To Read"
```

All eight `.py` files now compile cleanly.

### ⚠️ (c) The hardcoded username

Every data path contains `C:\Users\megha\`. Syncing to a second PC with a different Windows
username means every path breaks. If you only ever use machines logged in as `megha`,
you're fine. Otherwise the paths should move into `launcher_config.json` — a bigger change,
worth doing only if you actually need it.

## Data files: already untracked

All seven have been removed from git tracking with `git rm --cached`, which touches only the
git index — **your actual files are untouched on disk.** When you pull this branch into your
Reading folder, the spreadsheets, logs, and your `launcher_config.json` all stay exactly
where they are; git just stops carrying them.

The `.gitignore` covers them plus future logs, screenshots, and decision exports, so they
can't creep back in.

### One thing to know

`apply_reading_log.py` does **not** create `books_output.xlsx` or `my-reading-log.xlsx` if
they're missing — it prints `WARN: ... not found` and skips that half of the update
(lines 124 and 222). So on a new machine, wait for OneDrive to finish syncing your Reading
folder before running anything. A fresh `git clone` on its own won't give you those files,
by design.

> **Note:** this stops *future* commits from carrying these files, but the old versions stay
> in git history — the repo won't shrink. Since no real API key was ever committed
> (`openai_api_key` is `""` in the version that was pushed), that's harmless: the history
> just holds some stale spreadsheets. If you ever do push a real key, rotate it at
> platform.openai.com rather than trying to scrub history.

## Pulling updates

Once cloned, this is the whole thing — two lines:

```powershell
cd C:\Users\megha\book-tools
git pull
```

`git pull` knows which repo and branch to fetch from because `git clone` recorded it, so
there's nothing else to configure. Run it whenever you want the latest code.

If it refuses with *"Your local changes would be overwritten"*, you've edited a file that
also changed on GitHub. Check what's yours:

```powershell
git status
```

Then either keep your edits:

```powershell
git add -A
git commit -m "What I changed"
git pull            # merges the two sets of changes
```

or throw them away and take GitHub's version:

```powershell
git checkout -- .
git pull
```

`git checkout -- .` is permanent — it discards uncommitted edits with no undo. Only use it
when you're sure your local changes don't matter.

## Pushing your own changes

```powershell
git add -A
git commit -m "What changed"
git push
```

Your spreadsheets, logs, screenshots, and `launcher_config.json` are gitignored — they never
travel with a push and never cause a merge conflict.
